    Quarkus Challenge: Advanced Topics (Bonus Points!)

    🚀 Introduction & Organization

    Welcome! Today's objective is to tackle concrete technical challenges in Quarkus as a team.

    How We'll Work

    1. Form Groups: We will form 4 groups.
    2. Assign Missions: Each group will be assigned one of the four missions listed below.
    3. Objective: Your group must research, implement, and prepare a live demonstration of your solution.
    4. Bonus Points: A successful demonstration that proves your concept works will earn you bonus points for the module.

    The goal is not just to follow a tutorial, but to prove a concept.

    Good luck!

    🎯 Mission 1: Real-time Dashboard & Monitoring

    The Scenario

    Your application needs to display real-time data on a dashboard (e.g., a "live feed"). At the same time, the SRE team wants to know exactly how many users are connected to this feed in real-time, via their monitoring system (Prometheus/Grafana).

    Your Demonstration

    You must prove that you can: 1. Establish a real-time connection between the Quarkus backend and a simple front-end (an HTML/JS file is sufficient). 2. Create a metric (via Micrometer) that automatically increments/decrements when clients connect or disconnect. 3. The Proof: Show the web page receiving messages AND the Quarkus /q/metrics page where your custom metric (e.g., active_users) changes live.

    📚 Research & Guides

    • Quarkus - Getting started with WebSockets Next
    • Quarkus - Micrometer Metrics

    🎯 Mission 2: Secure Database Credentials

    The Scenario

    Your application connects to a database. Currently, the application.properties file contains this, which is a major security flaw (especially if the file is on Git):

    quarkus.datasource.username=admin
quarkus.datasource.password=ThisIsASecret!

    Your Demonstration

    You must refactor the application so that these credentials are never written in plain text in the configuration file again. The application must start and successfully connect to the database by fetching the credentials from an external source.

    • The Proof: Show us your application.properties file (it must no longer contain the secrets). Then, start the application and prove that it is correctly connected to the database (e.g., by calling an endpoint that performs a SELECT).

    📚 Research & Guides

    • Quarkus - Using a Credentials Provider
    • Quarkus - Secure JPA (Example of an external source)
    • Quarkus - Security Overview

    🎯 Mission 3: Build Properties & "Dead Code" Elimination & Conditional extentions

    The Scenario

    Quarkus claims to optimize applications at build time. We want to verify if this is true. If we "disable" a CDI bean using a build property, is that bean's code actually removed from the final JAR? Also explore Conditional extentions.

    Your Demonstration

    You must: 1. Create a simple CDI bean (e.g., @ApplicationScoped public class MyOptionalService). 2. Make its activation conditional on a property (e.g., @IfBuildProperty(name = "feature.X.enabled", stringValue = "true")). 3. Build the application twice: * mvn clean package (property absent = bean disabled) * mvn clean package -Dfeature.X.enabled=true (bean enabled)

    • The Proof: Using a Java decompiler or by inspecting the contents of the .jar (in target/quarkus-app/), prove to us that the MyOptionalService.class file is physically absent from the JAR when the property is absent, and present in the other one.

    📚 Research & Guides

    • Quarkus - Contexts and Dependency Injection (Search for @IfBuildProperty)
    • Quarkus - Conditional Extension Dependencies
    • Quarkus conditional extentions

    🎯 Mission 4: Surviving the Load (Load Shedding)

    The Scenario

    Your application works perfectly. But what happens if 10,000 users arrive at the same time? The application will saturate its threads and memory, and crash (a "cascading failure"). We want it to survive.

    Your Demonstration

    You must: 1. Create a simple endpoint (e.g., one that takes a short Thread.sleep(50) to simulate work). 2. Use a load testing tool (k6, Gatling, wrk, JMeter...) to "attack" your application and make it crash or become extremely slow. 3. Enable and configure "Load Shedding" in Quarkus. 4. Re-run exactly the same load test.

    • The Proof: Show us the load test results before (the application slows down, response times explode, 500 errors appear). Then, show us the test after: the application remains stable, response times for accepted requests are good, and excess requests are cleanly rejected (with 503 Service Unavailable errors).
